# Schema design: normalisation, keys and constraints

> **In one sentence:** Normalise so that each fact is stored once, denormalise only where you have measured the need and can keep the copy correct, choose keys by how they behave inside B-tree indexes, and declare every rule the database can check as a constraint, because the schema is the one layer every writer must pass through.

**Why it matters:** Schemas outlive the applications written against them. A poorly chosen key or a missing constraint accumulates duplicates and orphans silently, and the cleanup arrives years later as a migration nobody wants to run. "Natural or surrogate key" and "UUID or bigint" are interview staples because the answers depend on understanding indexes, not taste.

## The idea

**Normalisation is a tool, not a virtue.** Start with a spreadsheet-shaped table of orders:

```text
order_no | customer_email    | customer_name | product_sku | product_name | unit_price | quantity
1001     | alice@example.com | Alice         | W-1         | Widget       | 9.99       | 2
1001     | alice@example.com | Alice         | G-7         | Gadget       | 24.50      | 1
1002     | alice@example.com | Alice Smith   | W-1         | Widget       | 9.99       | 5
```

Alice's name is already inconsistent, the widget's price is repeated in every line that sells it, and a product nobody has ordered cannot exist. These are the update, insert and delete anomalies that normalisation removes: first normal form makes every cell atomic; second removes facts that depend on only part of a composite key (the product name depends on `product_sku`, not on the order); third and Boyce-Codd remove facts that depend on something other than the key (the customer name depends on the customer). The result is `customer`, `product`, `orders` and `order_line`, each fact stored once and joined by keys.

**Deliberate denormalisation.** Two reasons justify a copy. History: the price and product name on an order line are not copies of the product row but what the customer agreed to, and must not change when the catalogue does. And a measured hot read: a stored `order_count` on the customer, or a precomputed order `total`. Every copy needs an owner that keeps it correct (a trigger, or the one code path all writers use) and a way to detect drift; prefer computing on read until a measurement says otherwise, with a materialised view as the middle ground.

**Natural versus surrogate keys.** A natural key is a real-world identifier: email address, ISBN, organisation number. Natural keys change, get reused, are sometimes long, and as primary keys are copied into every child table and index. The working rule: a compact surrogate as the primary key and the natural key as a `UNIQUE` constraint, so uniqueness is still enforced. Pure association tables such as `order_line` can keep the composite natural key `(order_id, line_number)`.

**`bigint` identity, UUID v4 or UUID v7.** The choice is about index behaviour as much as about identity (item 2.3 shows the mechanism). After inserting a million rows into three tables that differ only in their key:

| Key | Index size | Leaf pages | Leaf density | Pages dirtied by the next 10,000 inserts |
|---|---|---|---|---|
| `bigint GENERATED ALWAYS AS IDENTITY` | 21 MB | 2,733 | 90% | 85 |
| `uuid DEFAULT uuidv4()` | 38 MB | 4,791 | 72% | 1,473 |
| `uuid DEFAULT uuidv7()` | 30 MB | 3,832 | 90% | 102 |

A random UUID lands anywhere in the tree, so every insert touches a random leaf, splits pages and leaves them 72% full; the index is almost twice the size of the integer one and every insert dirties pages that must be written and logged. UUID v7 (a millisecond timestamp followed by random bits; `uuidv7()` is built in from PostgreSQL 18) is time-ordered, so inserts go to the right edge like a sequence, while keeping what makes UUIDs attractive: generated by the client before the insert, unique across systems, safe to expose and revealing nothing about row counts. A common design uses both: `bigint` for the primary key and foreign keys, a `uuid` `public_id` with a `UNIQUE` constraint for everything that leaves the system.

**Constraints as the last line of defence.** Application code is one writer among many; migrations, batch jobs, support scripts and the next service write the same tables. `NOT NULL` is the default stance, relaxed per column with a reason. `CHECK` encodes domains (`quantity > 0`, a status list, a currency format) and cross-column rules. `UNIQUE` prevents duplicates the application "already checks for" (two concurrent inserts both pass the check); since PostgreSQL 15 `UNIQUE NULLS NOT DISTINCT` treats nulls as equal when that is what you mean. Foreign keys prevent orphans and define what happens on delete; PostgreSQL does not index the referencing column for you, and without that index every delete on the parent scans the child. An exclusion constraint generalises `UNIQUE` to "no two rows may overlap", the right tool for bookings and validity periods. `DEFERRABLE INITIALLY DEFERRED` postpones a check to commit for the rare cycle that needs it.

## Example: orders and order lines done well

```sql
CREATE TABLE customer (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      text NOT NULL UNIQUE CHECK (email = lower(email)),
    created_at timestamptz NOT NULL DEFAULT now()
);

-- product (id identity PRIMARY KEY, sku UNIQUE, name, unit_price CHECK (unit_price >= 0)) follows the same pattern

CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id   uuid NOT NULL DEFAULT uuidv7() UNIQUE,
    customer_id bigint NOT NULL REFERENCES customer (id),
    status      text NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
    currency    text NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
    created_at  timestamptz NOT NULL DEFAULT now(),
    paid_at     timestamptz,
    CHECK (paid_at IS NULL OR status <> 'pending')
);
CREATE INDEX orders_customer_id_created_at_idx ON orders (customer_id, created_at DESC);

CREATE TABLE order_line (
    order_id     bigint NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
    line_number  int NOT NULL CHECK (line_number > 0),
    product_id   bigint NOT NULL REFERENCES product (id),
    product_name text NOT NULL,                          -- what the customer saw, deliberately copied
    quantity     int NOT NULL CHECK (quantity > 0),
    unit_price   numeric(12,2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, line_number),
    UNIQUE (order_id, product_id)
);
CREATE INDEX order_line_product_id_idx ON order_line (product_id);

CREATE TABLE room_booking (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id int NOT NULL,
    during  tstzrange NOT NULL,
    EXCLUDE USING gist (room_id WITH =, during WITH &&)   -- needs CREATE EXTENSION btree_gist
);
```

The constraints answer back immediately and precisely:

```text
INSERT INTO orders (customer_id, currency) VALUES (1, 'nok');
ERROR:  new row for relation "orders" violates check constraint "orders_currency_check"
DETAIL:  Failing row contains (2, 01a16a1a-32d1-785c-..., 1, pending, nok, 2026-10-24 ..., null).

INSERT INTO room_booking (room_id, during) VALUES (7, tstzrange('2026-11-01 10:00+01', '2026-11-01 12:00+01'));
ERROR:  conflicting key value violates exclusion constraint "room_booking_room_id_during_excl"

DELETE FROM customer WHERE id = 1;
ERROR:  update or delete on table "customer" violates foreign key constraint "orders_customer_id_fkey" on table "orders"
```

Each of these is a bug that did not reach the data.

## Pitfalls

- Checking uniqueness in code before inserting. Two requests pass the check at the same moment and both insert. Only a `UNIQUE` constraint is race-free; use `INSERT ... ON CONFLICT` to handle the duplicate gracefully (item 1.5).
- Foreign keys without an index on the referencing column. Deleting a customer scans all orders; the lock is held for the whole scan (item 6.2).
- `varchar(255)` as a reflex, `char(n)`, `timestamp` without time zone, `money`, `serial` instead of identity columns. The PostgreSQL wiki's "Don't Do This" page lists each with the reason.
- Random UUID primary keys on large, insert-heavy tables. The table above shows the cost; use `bigint` or UUID v7.
- Denormalising without an owner. A copied `order_count` that two code paths update differently is worse than the join it replaced.
