# Consumer-driven contract testing with Pact, and where OpenAPI fits

> **In one sentence:** A consumer-driven contract is a file, generated by the consumer's own tests, that records exactly which requests the consumer makes and what it needs in the responses; the provider replays that file against its real implementation in its own build, so an incompatible provider change fails the provider's pipeline before deployment, with no shared test environment and no end-to-end test.

**Why it matters:** The failure that contract tests prevent is the quiet one: the inventory team renames `available` to `availableQuantity`, their tests pass, they deploy, and the order service starts reading `null` in production. An end-to-end test would have caught it a day later in a staging environment that is never quite the same as production. A contract test catches it in the inventory team's pull request, names the consumer that would break, and costs milliseconds. "What gets unit tests, integration tests and contract tests, and why" is on this domain's done-list, and the contract-test answer is: every seam between two independently deployed codebases.

## The idea

**Two views of an API.** An OpenAPI document (item 8.3) describes everything a provider offers: every path, parameter, status code and schema. It is the right artefact for contract-first design (write the document, review it, generate server interfaces and clients from it with openapi-generator, implement against the interfaces) and for documentation. It cannot tell the provider which parts anyone depends on. A consumer-driven contract describes what one consumer actually uses: three endpoints, four fields each. The provider can change anything outside that set freely and learns from a failing test when it touches something inside it. Use both: OpenAPI for the shape of the whole API, Pact for the seams that matter.

**How Pact works.** The description below is Pact JVM 4.6 with JUnit 5, writing version 3 pact files.

1. In the consumer's codebase, a test describes an interaction: given some provider state, when this request is sent, respond with this. Pact starts a mock HTTP server that serves that response, the consumer's real client code calls it, and the test asserts on what the client returned. The side effect is a JSON pact file (`target/pacts/order-service-inventory-service.json`) describing the interaction.
2. The pact file is published to a Pact Broker (or shared through the repository) tagged with the consumer's version.
3. In the provider's build, a verification test fetches every pact for this provider, starts the real application, puts it into each declared provider state through a `@State` method, replays each request, and checks the response against the pact's matching rules.
4. Before deploying either side, `can-i-deploy` asks the broker whether the version about to ship has a verified contract with every version currently in the target environment.

**Matching rules.** The consumer's expectations are written with type matchers (`stringType`, `integerType`), not literal values. The pact then says "a string called `productId`, an integer called `available`", and the provider may return any values of those types. Extra fields in the provider's response are ignored; missing fields and wrong types fail. The consumer should ask for the minimum it reads, so that the provider keeps the maximum freedom to change.

## Example: an order service that reads stock from an inventory service

The consumer side. `InventoryClient` is the real HTTP client the order service uses; only its base URL is pointed at Pact's mock server.

```java
import static org.assertj.core.api.Assertions.assertThat;

import au.com.dius.pact.consumer.MockServer;
import au.com.dius.pact.consumer.dsl.PactDslJsonBody;
import au.com.dius.pact.consumer.dsl.PactDslWithProvider;
import au.com.dius.pact.consumer.junit5.PactConsumerTestExt;
import au.com.dius.pact.consumer.junit5.PactTestFor;
import au.com.dius.pact.core.model.PactSpecVersion;
import au.com.dius.pact.core.model.RequestResponsePact;
import au.com.dius.pact.core.model.annotations.Pact;
import java.util.Map;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "inventory-service", pactVersion = PactSpecVersion.V3)
class InventoryClientPactTest {

    @Pact(consumer = "order-service")
    RequestResponsePact stockOfAKnownProduct(PactDslWithProvider builder) {
        return builder
            .given("product SKU-1 has 5 units in stock")
            .uponReceiving("a request for the stock of SKU-1")
                .path("/products/SKU-1/stock")
                .method("GET")
            .willRespondWith()
                .status(200)
                .headers(Map.of("Content-Type", "application/json"))
                .body(new PactDslJsonBody()
                    .stringType("productId", "SKU-1")
                    .integerType("available", 5))
            .toPact();
    }

    @Test
    void readsTheAvailableQuantity(MockServer mockServer) {
        InventoryClient inventoryClient = new InventoryClient(mockServer.getUrl());

        assertThat(inventoryClient.availableStock("SKU-1")).isEqualTo(5);
    }
}
```

The pact file this writes contains the request, the example response, and matching rules saying `productId` must be a string and `available` an integer. Nothing in the file mentions `InventoryClient`; the provider never sees the consumer's code.

The provider side, in the inventory service's test suite, against the real Spring Boot application on a random port:

```java
import au.com.dius.pact.provider.junit5.HttpTestTarget;
import au.com.dius.pact.provider.junit5.PactVerificationContext;
import au.com.dius.pact.provider.junit5.PactVerificationInvocationContextProvider;
import au.com.dius.pact.provider.junitsupport.Provider;
import au.com.dius.pact.provider.junitsupport.State;
import au.com.dius.pact.provider.junitsupport.loader.PactFolder;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.TestTemplate;
import org.junit.jupiter.api.extension.ExtendWith;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Provider("inventory-service")
@PactFolder("pacts")
class InventoryProviderPactTest {

    @LocalServerPort
    int port;

    @Autowired
    StockRepository stockRepository;

    @BeforeEach
    void pointPactAtTheRunningApplication(PactVerificationContext context) {
        context.setTarget(new HttpTestTarget("localhost", port));
    }

    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)
    void verifyEveryInteraction(PactVerificationContext context) {
        context.verifyInteraction();
    }

    @State("product SKU-1 has 5 units in stock")
    void productWithFiveUnits() {
        stockRepository.save(new Stock("SKU-1", 5));
    }
}
```

`@PactFolder` reads pact files from a directory for a first setup; in a real pipeline `@PactBroker` fetches them from the broker instead. The `@TestTemplate` expands into one test per interaction in every pact for `inventory-service`.

Now the inventory team renames the field. The provider test fails in their build with a body mismatch for the interaction "a request for the stock of SKU-1", reporting that `available` was expected and missing. The failure names the consumer and the interaction, so the inventory team knows who they would have broken and can either keep `available` alongside the new name (expand, migrate, contract; item 4.3) or talk to the order team first. The consumer never ran, and no environment was deployed.

Closing the loop, in each pipeline before deploying:

```bash
pact-broker can-i-deploy --pacticipant order-service --version "$GIT_SHA" --to-environment production
```

It answers yes only if the broker holds a successful verification between this consumer version and the provider version currently in production.

## Pitfalls

- Writing the pact from the provider's OpenAPI document instead of from the consumer's real needs. The pact then pins every field, the provider loses the freedom the technique was supposed to give, and nobody learns what is actually used.
- Literal values instead of type matchers. `.stringValue("productId", "SKU-1")` forces the provider's test data to match exactly; `.stringType` is almost always what you mean. The exception is a value the consumer branches on (a status code, an enum).
- Testing the provider's business logic through pacts. The pact checks the shape of the conversation; the provider's rules belong in the provider's own tests. Provider states should set up data, not assert behaviour.
- Pact for a public API with unknown consumers. Consumer-driven contracts need a known, finite set of consumers who run the tests. For a public API, OpenAPI with a backward-compatibility check on the document is the tool.
- Skipping `can-i-deploy`. Without it, a green provider build proves compatibility with the consumer version that published the pact, not with the one in production.
- Provider state methods that depend on execution order or leave data behind. Each state is set up fresh per interaction; clean up or use transactions.
- Contract tests for a seam inside one deployable. Two modules in one monolith share a compiler; the contract is the interface. Pact is for seams with separate deployments.
- Mocking the HTTP client in the consumer test "to keep it simple". The whole value is that the real client, serialisation and URL building run against the mock server.
